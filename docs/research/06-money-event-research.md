# 06. 돈(Money) 이벤트 연출 리서치 — 코인이 나는 풀스크린 "이벤트" 설계 근거

> 작성일: 2026-10-05. 대상: Lot & Roll (Money Poly, 4인 패스앤플레이 보드게임, 통화 단위 `만`).
> 목적: 지불·수령·전원 징수·구매·건설·인수·파산 같은 **돈의 순간**을 상위 모바일 게임처럼 "풀스크린 이벤트 + 코인 연출"로 만들기 위한 근거와 **30 fps 프레임 단위 권장안**.
> 이 문서만 새로 작성했다. **코드는 건드리지 않았다.**
>
> **근거 표기** (`04`, `05` 문서와 동일 규칙)
> - **[V]** 이 세션에서 직접 fetch/명령/파일 열람으로 확인.
> - **[S]** 웹 검색 결과 요약(스니펫)에만 근거. 원문 확인 실패.
> - **[K]** 작성자의 배경 지식/업계 관행/추정. 스파이크·실측으로 검증 필요.
> - **[D]** 이 문서가 새로 제안하는 **설계 값**(근거가 아니라 결정).
>
> **조사 한계 (반드시 읽을 것)**
> 1. 샌드박스 프록시가 `web.dev`, `blakecrosley.com`, `mariowiki.com`, `fandom.com`, `gamemeca.com`, `wikipedia.org` 등을 차단했다(WebFetch `EGRESS_BLOCKED`). fetch에 성공한 것은 `developer.android.com` 햅틱 문서 하나뿐이다.
> 2. 웹 검색은 게임 규칙·공략 글 위주로 나왔고, **프레임/ms 단위 연출 서술은 거의 없었다.** 검색 결과의 상당수는 품질이 낮은 미러/스팸 도메인이다(출처 목록에서 신뢰도 표기).
> 3. 따라서 **개별 게임의 ms·코인 수는 전부 [K] 재구성(영상 기억 + 업계 관행)이며 측정값이 아니다.** "구조(비트 순서)"는 신뢰할 수 있지만 숫자는 "이 정도 규모"로만 읽고, 우리 값은 §9의 [D]를 기준으로 한다. 프레임 단위 확인은 접근 가능한 환경에서 화면 녹화(60 fps)를 떠서 후속 검증을 권한다(§10).
> 4. 이 문서의 이전 연구 `05-vfx-research.md`는 Canvas2D 파티클 엔진을 권장했다. **이번 요청의 제약은 "Android 빌드에서 canvas 불가(DOM/CSS만)"**이다. 코인 이벤트는 §8의 DOM 풀링 방식으로 설계했으며, 기존 canvas 경로와 독립적으로 동작한다. 두 문서의 충돌은 §8.0에 정리했다.

## 0. 결론 (TL;DR)

| 항목 | 결론 |
|---|---|
| 공통 비트 | **기대(4–8f) → 스폰(스태거 1–2f) → 이동(호, 12–16f) → 도착(코인별 링/범프/클링크) → 카운트업(ease-out cubic) → 안정(6–9f)** — 모든 돈 이벤트가 같은 문법을 쓰고, 금액 크기는 **코인 수·지속시간·사운드 에스컬레이션**으로만 달라진다. |
| 핵심 규칙 1 | **숫자와 더미는 타이머가 아니라 코인 이벤트에 동기화**한다. 출발 지갑은 코인이 떠날 때마다 줄고(숫자 −청크, 더미 높이 −1), 도착 지갑은 코인이 닿을 때마다 늘어난다. 한 번에 끝에서 값을 바꾸면 "돈이 이동했다"는 인과가 사라진다. |
| 핵심 규칙 2 | **내는 소리 ≠ 받는 소리.** 지불은 피치 하강 + 낮은 "툭", 수령은 피치 상승 + 마지막 "챠링". 같은 코인 샘플이라도 방향을 소리로 구분한다. |
| 핵심 규칙 3 | 이벤트당 **1.2–3.0 s(36–90 프레임)**, 어디든 탭하면 **≤4프레임**에 최종 상태로 점프(스킵). 같은 종류가 연속되면 0.7배속(터보). |
| 지갑 더미 | 금 = 1,000만 / 은 = 100만 / 동 = 10만, **스택 3개(DOM 3노드)**, 금 스택만 로그 압축, 10,000만 이상은 보석 1개. 지갑당 최대 **6노드**. |
| 렌더 | DOM/CSS 전용. **코인 풀 12–16노드**, 동시 비행 ≤12, transform/opacity만, 비행 컨테이너 1개에 레이어 1개(기존 레이어 피크 17/20 [V: 05 §2.1] → 여유 3). |
| 아트 | SVG + WebP는 **`image-rendering: auto`(부드럽게)**. 코인 스프라이트는 표시 크기의 ×2.5(DPR) ×1.25(팝) 이상으로 구워 **축소만** 한다. 픽셀아트용 `pixelated`는 쓰지 않는다. |
| 사운드 | 코인 클링크 4–8종 라운드로빈 + 피치 ±1 반음, 코인 버스 동시 6보이스(전체 SFX 8), 최소 간격 1프레임, 수령 시 펜타토닉 상승 래더, 카운트업 틱 ≤15 Hz. |
| 햅틱 | 코인마다 X. **첫 도착(light) / 3번째 도착마다(tick) / 마지막 도착(success·medium) / 스탬프(heavy)**, 초당 ≤10회. 안드로이드는 CLICK/TICK 같은 사전 정의 효과 우선, 버즈 패턴 금지 [V]. |

### 1.3 공통 패턴 추출

1. **방향성**: 상위 게임 대부분 "코인은 항상 도착지(카운터)로 빨려듦". 1인 시점이라 도착지가 고정 HUD. 우리는 도착지가 **4개 좌석 패널 중 하나**이므로, 출발/도착 모두 패널 좌표를 쓴다(§7).
2. **크기 = 단계 점프**: 슬롯류는 연속 스케일이 아니라 **4단계(20×/40×/80×/Max) 점프** [S]. 우리도 금액을 S/M/L/XL 4단계로 나눠 연출 길이·코인 수·딤·쉐이크를 단계별로 점프시킨다(§9.0).
3. **정보 채널 중복**: Balatro는 쉐이크 크기, 피치, 파티클 수 모두 점수와 비례 [S]. 우리도 금액 → (코인 수, 지속시간, 피치 상한, 쉐이크 px, 딤 %) 5채널 동시 스케일.
4. **음악을 끊지 않는 카운트업**: 롤업 틱이 음악 위에 멜로디로 올라탐 [S]. 우리는 음악 덕킹 −4~−6 dB만 하고 카운트업을 같은 키의 펜타토닉 틱으로 구성.
5. **스킵 가능성**: 슬롯/상자류는 탭으로 롤업 즉시 완료가 표준 [K]. 반복 빈도가 높은 우리 게임(턴마다 돈 이벤트)에서는 스킵 + 터보가 필수.

### 2.2 호(arc) 형태

- **2차 베지어 + 스케일 고도 착시**: 시작 P0, 도착 P2, 제어점 P1 = 현의 중점 + 수직 방향 `0.15–0.25 × 거리`. 코인이 "공중에 뜬" 높이는 y오프셋 대신 **스케일 `1 + 0.25·sin(πt)`**로 표현(2.5D, §6). [D]
- **스폰 홉(중력형)**: 스폰 직후 4–6 f 동안 위쪽으로 24–40 px 튀어 오르며 좌우 ±24–30 px 무작위. `y = v0·t − ½g·t²` 형태를 4–6개 키프레임으로 사전 샘플. [D]
- **자석 가속**: 홉 이후 도착까지 `t^1.6` ease-in(처음엔 느리고 끝에서 빨려듦). 1인 시점 게임의 "HUD로 빨려듦" 느낌 [K]. 도착 직전 속도가 최대이므로 도착 이벤트(링+클링크)가 시각적으로 "탁" 박힌다.
- 코인별 호 편차: 제어점 높이 ±20 %, 스폰 홉 각도 ±15°, 이동 시간 ±1f — 무작위는 **시드 RNG**(재현성)로 뽑되 게임 상태 RNG와 분리(순수 연출용). [D]

### 2.3 출발 지갑 고갈 / 도착 지갑 충전

| 표현 | 출발(지불자) | 도착(수령자) |
|---|---|---|
| 더미 | 코인이 떠날 때 그 코인 가치만큼 스택에서 1개 제거(스택 높이 −1, 윗면 코인 팝아웃 2f) | 코인 도착 시 스택 높이 +1(최상단 코인 "착지 바운스" 2f) |
| 숫자 | 코인 단위로 `−청크` 계단식(떠나는 f에 맞춰) | 도착 f에 `+청크`, 최종 카운트업으로 마무리 |
| 색 | 첫 코인 이탈 시 적색 틴트 펄스(4f) | 첫 도착 시 소유자 색 링 + 금색 글로우 |
| 부유 텍스트 | f0 `−340` 패널 위로(적색, 700 ms) | 첫 도착 f `+340` 팝(0.6→1.25→1.0, 8f) |
| 모션 | 패널 스케일 1→0.97→1(수축) | 패널 스케일 1→1.06→1(범프)/코인마다 소형 |

청크 = `amount / N`(정수, 마지막 코인이 나머지 흡수). 지갑 숫자는 항상 **정수 `만`**이므로 청크 반올림을 마지막 코인에서 보정한다. [D]

### 2.4 카운트업 속도 곡선

- **이징**: `v(t) = 1 − (1 − t)³` (ease-out cubic) — 처음 빠르고 끝에서 감속해 "마지막 자릿수가 굴러 들어오는" 느낌. 슬롯의 롤업은 중간 가속→끝 감속이 표준 [K]. [D]
- **지속시간**: `dur_ms = clamp(500 + 300·log10(1 + amount/10), 500, 1100)` → 30만 ≈ 680 ms(20f), 300만 ≈ 947 ms(28f), 3,000만 이상 1,100 ms(33f). [D]
- **갱신율**: 30 fps 이벤트 클럭에서 매 프레임 값을 계산하되 **DOM 텍스트 쓰기는 프레임마다 1회**(10–30 Hz). 기존 패널은 ≈10 Hz [V: 05 §1.3]. 숫자 폭 점프를 막기 위해 `font-variant-numeric: tabular-nums` + 고정 폭 컨테이너. [D]
- **자릿수 롤(digit roll)**: 풀 구현은 자릿수마다 transform 노드(레이어 비용)이므로 **비권장**. 대안으로 **마지막 자리 하나만** `translateY` 한 칸 롤(옵션). [D]
- **틱 사운드**: 값이 `step = max(10, roundTo10(amount/16))` 증가할 때마다 1틱, 상한 15 Hz. 마지막 20 % 구간은 틱 간격 ×1.5(감속 청각 신호). [D]

### 2.5 화면 딤 / 비네트 / 카메라

- **딤**: 고정 오버레이 `div` 1개의 `opacity` 0→목표(5f easeOut) → 이벤트 끝에서 복귀(8f). `filter: brightness`나 `backdrop-filter`는 쓰지 않는다(페인트/레이어 비용). [D]
- **비네트**: 방사형 그라디언트를 미리 칠한 오버레이(opacity만 애니메이션). 딤과 한 노드로 합칠 수 있다(가운데 투명한 radial-gradient + 가장자리 어둡게 → opacity 하나). [D]
- **카메라 펀치(줌)**: `.table` 래퍼에 `scale(1→1.015→1)` 6–8f. 1.03을 넘기면 래스터 선명도 저하 위험(§6.3). [D]
- **쉐이크**: `.table`에 translate 감쇠 진동, 회전 ≤0.3°. 4인 테이블탑은 회전축이 없으므로 **쉐이크는 방향 중립(원형 진동)**으로 한다(한쪽 사용자에게만 크게 보이는 수평 편향 금지). [D]

| Monopoly GO "전원에게서 수령" | Monopoly GO | 여러 상대에게서 현금이 동시에 날아와 카운터로 | [K] 재구성 |

### 5.2 중앙 팟 경유 패턴의 장점/타이밍 [D]

- **경유 이유**: 4인이 한 화면을 공유하므로, "3명이 동시에 수령자에게 코인을 쏟아붓는" 직접 이동은 시선이 갈라지고 경로가 서로 겹친다. **중앙 팟에 모으면 모두의 시선이 한 점에 모이고**(공유 초점), 합계 숫자가 눈에 들어오며, 이후 수령자로 가는 단일 스트림이 인과를 명확히 한다.
- 타이밍: 징수 스트림은 **지불자 순서대로 6f 간격**(순차 착각 방지), 팟 홀드 8–12f(합산 확인·앤티시페이션), 분배/수령 스트림은 **1f 스태거 고속**(압축 방출, "쏟아져 나가는" 느낌).
- 수령자가 여럿인 "전원 지급"은 팟에서 **수령자별 5f 간격**으로 방출(챠링 사운드 최소 간격 150 ms 규칙과 정렬, §9.3).

| 숫자 크기 | 부유 텍스트 최소 28 CSS px, 대형 이벤트 40+ px, 윤곽선(검정 2px) + 소유 색 배경 칩. |

| 트릭 | 방법 | 비용 |
|---|---|---|
| 스케일 = 높이 | 호 정점에서 `scale 1.0→1.25→1.0`(`sin` 곡선) | transform만, 무료 |

| 드롭 섀도 | 코인 스프라이트에 **그림자를 굽는다**(오프셋 소프트 쉐도). 비행 클러스터당 **그라운드 섀도 타원 1노드**(스케일/불투명도만 변화). `filter: drop-shadow`/`box-shadow` 애니메이션 금지 | 노드 +1 |

| 스택 두께 | 스택 1노드 + `repeating-linear-gradient`로 측면 줄무늬, 위에 윗면 타원 코인 | 노드 1/스택 |

### 6.3 아트 업스케일링 (SVG + WebP 스프라이트)

| 질문 | 답 | 태그 |
|---|---|---|
| `image-rendering` 값 | `auto`/`smooth`(쌍선형), `crisp-edges`(최근접 계열), `pixelated`(Chrome 지원). 래스터는 기본 부드럽게 업스케일됨, 픽셀아트·클로즈업에는 부적합 | [S] (MDN, zpl.fi 검색 요약) |
| 우리 아트에 적합한 값 | SVG 벡터 + 고해상도 WebP는 **`auto` 유지**. `pixelated`는 우리 에셋에 쓰면 계단 현상이 생김 | [D] |
| 해상도 규칙 | 코인 표시 최대 48 CSS px, 안드로이드 DPR 2.6–3.0, 팝 스케일 1.25 → 스프라이트 셀 **최소 48×3×1.25 ≈ 180 → 192 px**(2의 배수·패킹 편의). **다운스케일만**, 업스케일 금지. | [D] |
| `will-change: transform` 래스터 스케일 | 레이어를 승격한 시점의 스케일로 래스터되어, 이후 스케일 업하면 흐려질 수 있음. 완화: 최대 스케일에서 시작해 줄이거나, 업스케일을 ≤1.25로 제한하고 소스를 크게 굽는다. | [K] — 대상 WebView에서 실측 필요 |
| 정수 픽셀 스냅 | 정지 구간(지갑 더미, 스탬프)은 translate를 정수 px로 반올림해 서브픽셀 블러 방지 | [K] |
| SVG를 `<img>`로 쓸 때 | 레이아웃 크기로 래스터 → transform 스케일 시 재래스터가 일어나지 않을 수 있어 흐려짐. **코인은 WebP 스프라이트로 구워서 쓰고**, SVG는 정적 큰 요소(건물·배경)에 사용 | [K] |
| 픽셀아트 케이스(만약) | `image-rendering: pixelated` + 정수 배율 + 정수 px 이동, Firefox 호환은 `crisp-edges`/SVG `image-rendering` 속성 병용 | [S] (zpl.fi 검색 요약) |

## 7. DOM/CSS 전용 퍼포먼스 설계

### 7.0 제약 재확인

- 05 문서 §2.1 [V]: 30 fps 상한, **유휴 0**(사람 차례 대기 중 Layout/Paint/rAF 0), 레이어 피크 ≤20(현재 17 → **여유 3**), 레이어 메모리 ≤100 MB(현재 89 MB → ~11 MB). 이번 요청은 canvas 금지 → 코인은 DOM.
- 일반 원칙(검색 확인 [S]): `transform`/`opacity`만 컴포지터에서 처리 가능, `will-change`는 **짧게·소수에만**(남용하면 레이어·메모리 증가), 레이아웃 유발 속성(top/left/width/height) 애니메이션 금지 (frontendchecklist, motion.dev, mspk.substack 검색 요약).

### 7.1 노드/레이어 예산 [D]

| 항목 | 상한 | 이유 |
|---|---|---|
| 풀 코인 노드 | **16** (생성 1회, 재사용) | 기본 호 14f + 스태거 2f → 동시 비행 ≈7; 고속 스트림(1f) 14f → 14 → 풀 16 |
| 동시 비행 코인 | **≤12**(XL 제외 ≤10) | 레이어/페인트 예산 |
| 비행 컨테이너 | 1개 (`.fx-coins`, `position:fixed; inset:0; contain: layout paint style; pointer-events:none`) | 컨테이너가 승격 레이어 1개, 코인은 그 안에서 **개별 승격 없이** transform 변경 [K — 실측 필요, 대안: 코인별 will-change] |
| 지갑 더미 | 지갑당 **3 스택 + 보석 ≤3 = ≤6 노드** × 4 = 24 정적 노드 | 정지 상태는 승격하지 않음 |
| 링/스파클 풀 | 링 8, 스파클 16 (opacity+scale만) | 이벤트 중에만 표시 |
| 딤/비네트 | 노드 1 | opacity만 |
| 추가 레이어 합계 | **≤3**(코인 컨테이너, 딤, 이벤트 배너) | 17 + 3 = 20 |

> 위 "코인은 컨테이너 안에서 개별 승격 없이" 가정은 **측정이 필요하다.** 컨테이너 레이어 안에서 자식의 transform을 JS로 매 프레임 바꾸면 컨테이너 래스터가 반복되므로, 코인 12개(각 ≤48 px) 정도면 면적이 작아 OK일 가능성이 높다(05 §2.3 [M]은 면적이 비용을 지배한다고 보고). 대안 A는 코인별 `will-change: transform`(최대 12 레이어, 예산 초과 위험), 대안 B는 WAAPI 키프레임(compositor 구동, 코인별 승격 발생). **실측 후 A/B/현재안 중 선택**(§10 과제 1).

### 7.2 구동 방식

| 방식 | 장점 | 단점 | 권장 |
|---|---|---|---|
| WAAPI `el.animate()` + 사전 샘플한 6–8 키프레임(`translate3d` + `scale`) | 컴포지터 구동(메인 스레드 블록에도 부드러움), 도착 이벤트는 `onfinish` | 코인마다 레이어 승격, 30 fps 정렬 어려움(60 Hz 구동) | 코인 수 적을 때(≤8) |
| JS 30 Hz 클럭 + `style.transform` 일괄 쓰기(기존 `onFrame` 재사용) | **전역 30 Hz 클럭과 위상 일치**, 이벤트 타임라인/스킵 제어가 쉬움(프레임 번호로 상태 계산 = 결정적) | 메인 스레드 의존 | **기본 권장**: 타임라인을 프레임 함수로 표현하면 스킵(마지막 프레임으로 점프)이 자명 |
| CSS `offset-path` | 코드 간단 | 컴포지터 가속 아님 [K], 지원/성능 불확실 | 비권장 |

→ **기본 구동은 기존 30 Hz `onFrame` 클럭 + 프레임 함수.** 이벤트 타임라인은 `state(frame)`의 순수 함수이므로 "스킵 = 마지막 프레임 한 번 그리기"로 끝난다.

### 7.3 스프라이트 시트 / 회전 코인

- 요청된 기법: 배경 위치 `steps()`. `background-position` 애니메이션은 **컴포지터 구동이 아니라 페인트가 발생**한다 [K]. 코인은 48 px 정도로 작아 비용이 낮지만, 12개 동시면 매 프레임 12번 페인트.
- 권장 대안: **스트립을 자식 노드로 두고 부모는 `overflow:hidden`, 자식에 `transform: translateX(-N*frameW)`를 `steps(N)` 타이밍으로 이동** — `transform`이므로 컴포지터 친화적 [K]. 단, JS 프레임 함수에서 `frame % 8`로 직접 translate하는 것이 30 Hz와 가장 잘 맞는다.
- 스프라이트 시트 구성: 코인 3등급(금/은/동) × 8프레임 회전 = 24셀 + 보석 8프레임 → 256×… WebP 1장(알파). 05 §0에서 측정한 WebP 인코딩 경로(Chromium 자체 인코더) 재사용 가능 [V: 05].

### 7.4 기타 규칙 [D]

| 규칙 | 설명 |
|---|---|
| 풀링 | 이벤트 시작 시 풀에서 N개 확보, 도착/종료 시 `visibility:hidden` + 풀 반환. `display:none` ↔ 표시 전환 반복은 레이어 재생성 비용. |

## 9. Money Poly 적용 권장안

### 9.0 공통 템플릿 [D]

- 시계: 30 fps, 1f = 33.3 ms. 모든 이벤트는 **프레임 함수 `render(f)`** 로 표현(순수). 스킵 = `f = end`로 1회 렌더.
- 금액 단계(연출 규모 4단계 점프, 슬롯 Big Win 단계 구조 참고 [S]):

| 단계 | 조건(예: 통행료/지불액) | 코인 수 | 이벤트 길이 | 딤 | 쉐이크 | 피치 래더 상한 |
|---|---|---:|---|---|---|---|
| S | < 100만 | 3–5 | 36 f (1.2 s) | 0 % | 0 | +4 반음 |
| M | 100–499만 | 6–8 | 54 f (1.8 s) | 25 % | 2 px | +7 |
| L | 500–999만 | 10–12 | 72 f (2.4 s) | 35 % | 4 px | +9 |
| XL | ≥ 1,000만 또는 지불자 현금의 ≥ 40 % | 14–16 | 84–90 f (2.8–3.0 s) | 50 % | 6 px | +12 |

- 코인 수 = 금액 분해 기반이지만 최소 3개·최대 16개로 클램프(§9.2). 코인이 보여주는 것은 "금액 비율", 정확한 값은 숫자.
- **스킵**: 이벤트 f6 이후 어디든 탭(또는 우측 하단 "건너뛰기" 칩이 f6에 페이드인) → 남은 코인을 **4f 안에 한 묶음으로 수렴**시키고 최종 상태(숫자·더미·소유 색)를 렌더, 사운드는 수령이면 챠링 1회/지불이면 툭 1회만. 엔진 상태는 이미 확정되어 있으므로(리듀서가 먼저 적용) 스킵은 **연출만 건너뛴다**.
- **터보**: 동일 이벤트 종류가 연속 2회째부터 0.7배속(프레임 간격은 유지하고 키프레임을 0.7로 압축), 3회째부터 코인 수 ½.

### 9.2 지갑 더미 단위/스케일링 [D]

**액면가**

| 등급 | 값 | 스프라이트 | 용도 |
|---|---:|---|---|
| 동(bronze) | 10만 | 작은 갈색 코인 | 세무서 10 % 반올림 단위, 소액 |
| 은(silver) | 100만 | 중간 은색 코인 | 기부금(100), 소액 통행료 |
| 금(gold) | 1,000만 | 큰 금색 코인 | 서울/뉴욕급, 시작 자금 구성 |
| 보석(gem) | 10,000만 | 청색 다이아 | 초부자 상태 표시(드묾) |

**분해(지갑 더미)**: `g = ⌊v/1000⌋`, `s = ⌊(v mod 1000)/100⌋`, `b = ⌊(v mod 100)/10⌋`. 10만 미만 잔돈은 무시(숫자로만 표기).
시작 자금 3,000만 = 금 3 / 은 0 / 동 0. 월급 300만 = 은 3. (대지 가격 100–1,000만은 은 1–9 또는 금 1.)

**가시 코인 수(로그 압축)**: 은·동은 자릿수 0–9라 **정확히 표시**. 금은 `n_gold`가 커질 수 있어 압축:

```
vis(n) = n ≤ 5 ? n : min(9, 5 + ⌊log2(n − 4)⌋)        // n=6→6, 8→7, 12→8, 20→9(상한)
gem    = ⌊v / 10000⌋ (최대 3개 표시, 초과 시 "×N" 칩)
```

가시 코인 최대: 금 9 + 은 9 + 동 9 + 보석 3 = **30개**지만 DOM 노드는 **스택 3개 + 보석 ≤3 = 6노드**(스택 1개 = 노드 1, 측면 줄무늬는 `repeating-linear-gradient`, 윗면 타원 코인 1장). 스택 높이는 `vis(n) × 5 px`(금 스택 최대 45 px).

**읽기**: 시작 3,000만 → 금 3(높이 15 px), 5,000만 → 금 5(25 px), 12,000만 → 금 9 + 보석 1. 파산 직전(<100만) → 금 0 + 동 몇 개: **금 스택 유무와 높이**가 부자/빈자를 한눈에 구분. 중앙 팟은 같은 컴포넌트를 스케일 1.5로 사용.

**비행 코인 구성**: 금액 분해 코인(금/은/동)을 쓰되 최소 3개·최대 16개로 클램프(동 코인부터 버려서 16 이하로, 3개 미만이면 장식용 동 코인 추가). 코인별 가치 청크 = `amount / N`, 마지막에 나머지 흡수. 지갑 더미/숫자는 코인 이벤트에 따라 이 청크로 갱신하고, 마지막 코인에서 정확한 정수값에 도달한다.

**레이어링 규칙**

1. **동시 보이스**: 코인 버스 ≤6, 전체 SFX ≤8. 초과 시 우선순위 낮은/오래된 보이스부터 중단. 우선순위: `chaChing` > `stampThud`/`landmarkStinger` > `coinStack`/`potStack` > `coinClink*` > `countTick`.
2. **챠링 간격**: 같은 큐 150 ms(≈5f) 미만 간격 금지(E7 수령자 5f 간격이 이 규칙에서 나옴).
3. **지불 ≠ 수령**: 지불 이벤트는 `coinClinkDown`(하강) + 낮은 툭으로 끝나고 **챠링을 쓰지 않는다**. 수령/이득만 상승 래더 + 챠링.
4. **방향 패닝(옵션)**: 좌석 방향에 따라 ±0.4 스테레오 패닝(슬롯류의 좌→우 패닝 [S]을 4좌석으로 확장). 모노 스피커 기기에서도 깨지지 않게 EQ로 구분은 유지.
5. **스킵 시**: 진행 중인 코인 보이스를 15 ms 페이드아웃 → 수령이면 `chaChing` 1회, 지불이면 `stampThud` 소형 1회.
6. **음악 덕킹**: 대형(L/XL) 이벤트만 −6 dB, S/M은 −3 dB.

## 12. 10줄 요약

1. 공통 비트 = 기대 → 스폰 → 이동 → 도착 → 카운트업 → 안정; 금액은 **코인 수·길이·딤·쉐이크·피치 상한**의 4단계(S/M/L/XL) 점프로만 구분.
2. 숫자/더미는 타이머가 아닌 **코인 이탈·도착 이벤트에 동기**(출발은 떠날 때 감소, 도착은 닿을 때 증가).
3. 이벤트 길이 36–90 f(1.2–3.0 s), 탭 스킵은 ≤4 f에 최종 상태 렌더(엔진 상태는 선확정), 연속 시 0.7× 터보.
4. 코인: 호는 2차 베지어(제어점 0.15–0.25×거리) + 스케일 `1+0.25 sin πt`로 높이 착시, 스폰 홉 4–6 f 후 `t^1.6` 자석 가속, 기본 스태거 2 f/고속 1 f, 이동 14 f.
5. 카운트업 = ease-out cubic, `500+300·log10(1+amount/10)` ms(500–1100), 틱 ≤15 Hz, 폭 고정 tabular-nums.
6. 중앙 팟 경유(전원 징수·지급): 지불자 6 f 간격 징수 → 팟 홀드 8–12 f(앤티시페이션 떨림) → 1 f 스태거 분배, 팟 합계는 4방향 복제 숫자.
7. 지갑 더미: 금 1,000 / 은 100 / 동 10 / 보석 10,000, **3스택(3노드)**, 금만 로그 압축 `vis(n)=5+⌊log2(n−4)⌋`, 지갑당 ≤6노드.
8. DOM 전용: 코인 풀 16·동시 ≤12, 구동은 기존 30 Hz 클럭 프레임 함수, transform/opacity만, 글로우·그림자는 굽기, 레이어 추가 ≤3(현재 17/20) — **컨테이너 1레이어 가정은 실측 필요**.
9. 사운드: 클링크 4–8종 라운드로빈 ±1 반음, 코인 버스 6/전체 8 보이스, 수령=상승 펜타토닉 + 챠링, 지불=하강 + 툭(챠링 없음), 챠링 간격 ≥150 ms, 음악 덕킹; 햅틱은 코인마다가 아니라 1번째/3번째마다/마지막/스탬프(≤10회/s, CLICK·TICK 사전 정의 효과 [V]).
10. 신뢰도 경고: 샌드박스 차단과 저품질 검색 결과 때문에 개별 게임의 ms·코인 수는 **전부 [K] 재구성**이며 구조만 신뢰 가능 — 60 fps 화면 녹화로 후속 실측과 실기기 레이어/선명도 측정이 필요(§10).
