# 주사위 던지기 리서치: 버튼 대신 "꾹 누르고 밀어 던지기"

2026-10-06. 요청: 굴리기 버튼 대신, 차례가 오면 주사위가 흔들리며 던지라고 알려 주고, 가운데를 누르면
주사위가 마구 흔들리고, 누른 채 밀면 그 방향으로 날아가 튕기며 구르는 "실감 나는" 던지기. three.js +
물리 엔진이 맞는지, 과한지, 더 쉬운 길이 있는지.

## 0. 결론 먼저

- **가능하다.** 세 가지 길이 있고, 추천은 **B: 라이브러리 없는 "연출 물리"**(아래 §3)다. 지금 코드의
  투영 큐브와 30 Hz 클럭 위에 포물선 + 벽 튕김 + 회전 감쇠를 직접 쓰는 방식. 새 의존성 0, WebGL 0,
  엔진의 주사위 값(시드 RNG)과 완전히 호환. 작업량 1.5~2일(제스처 1일 + 다듬기 1일).
- **A: three.js(또는 Babylon) + 물리 엔진은 이 프로젝트에서는 과하다.** 보기엔 가장 진짜 같지만,
  (1) 삼성 태블릿 WebView가 지금 2D 캔버스도 흰 사각형으로 그리는 원인을 아직 못 찾았는데 WebGL은 그보다
  더 큰 미지수, (2) 번들 +250~400 KB(gz), (3) 던지는 1.5초 동안 GPU 레이어·배터리, (4) 결과를 엔진 값에
  맞추는 트릭이 추가로 필요. 태블릿에서 WebGL이 확인된 뒤 "실감 주사위" 옵션으로 붙이는 것은 가능.
- **C: 미리 구운 스프라이트**(3D로 렌더한 프레임을 아틀라스로)는 런타임 비용은 가장 싸지만, 방향 × 최종
  눈 × 프레임 수가 곱해져 아틀라스가 커지고, 손가락 방향을 자유롭게 따라가지 못한다. 보류.

## 1. 지금 코드가 이미 가진 것

- `src/ui/stage/Dice.ts`: 주사위는 **2D 변환으로 그린 직교 투영 큐브**(`cubeFaces`)다. 멈춘 주사위는
  DOM 면 6장(실제 3D 렌더링 컨텍스트 없음, 레이어 1장), 굴리는 ~900 ms 동안은 같은 투영을 **임시 소프트웨어
  캔버스 한 장**에 30 Hz로 그린다(`tumble`, 두 주사위 함께, 끝나면 캔버스 제거). 착지 바운스 곡선
  `BOUNCE`도 있다.
- `src/ui/stage/prompts.ts`: 굴리기 버튼은 이미 **꾹 누르면 흔들기**(`dice.shake`, 딸깍 소리, 햅틱)이고,
  규칙 옵션 B7 "주사위 게이지"(`diceGauge`)가 켜져 있으면 누른 시간으로 게이지가 왕복한다. 떼면 `Roll`.
- `src/ui/stage/CpuHand.ts`: CPU 손이 굴리기 버튼을 누르고 있는 동안 주사위가 딸깍거린다(`isHeld`).
- 소리: `dice-shake`, `dice-land`, `doubles`(Web Audio 합성, `src/ui/audio/synth.ts`).
- 주사위 값은 **엔진이 시드 RNG로 먼저 정한다**(`reducer.ts nextDice`). 연출은 그 값에 "도착"해야 한다.
  어떤 방식이든 "진짜로 굴러서 나온 눈"이 될 수는 없고, 그래 보여야 할 뿐이다. 이것은 3D 물리를 쓰는
  상용 앱들도 같다(아래 §2).

## 2. A안: three.js / Babylon + 물리 엔진

조사한 것:
- `@3d-dice/dice-box`: Babylon.js + Ammo.js, 웹 워커 + OffscreenCanvas, 압축 후 약 400 KB~1 MB.
  결과 강제 지원. 작성자가 결정론 때문에 Rapier로 바꿨다가 "결정론이 전혀 되지 않았다"고 기록.
  (fantasticdice.games 문서)
- `threejs-dice`(cannon / cannon-es 포크): "던진 뒤 어느 면이 위로 올지 지정"을 지원. 방식은 **먼저 물리를
  끝까지 돌려 보고(몇 ms), 위로 온 면을 읽은 뒤, 원하는 눈이 그 면에 오도록 눈 텍스처/메시를 회전**시키는
  것. 플레이어는 차이를 못 느낀다. Codrops의 "Dice Roller with Three.js and Cannon-es" 튜토리얼도 같은
  구조(물리 → 착지 면 판정).
- 번들: three.js 코어 ~150 KB gz, cannon-es ~40 KB gz, Rapier(wasm) ~1.5 MB. Babylon은 더 크다.

이 프로젝트에서의 문제:
1. **기기 미지수.** `docs/HANDOFF.md`: 삼성 4:3 태블릿이 효과 캔버스를 흰 사각형으로 그렸고 원인은
   미확인, Android 앱은 캔버스 효과를 기본으로 끈 상태. 지금 주사위 굴림 캔버스조차 태블릿에서 흰 박스가
   보이는지 아직 확인 과제(HANDOFF 열린 항목 1). WebGL 컨텍스트는 그 위에 또 하나의 가정이다.
2. **성능 정책.** 유휴 0, 30 fps 캡, 레이어 피크 20(지금 19). WebGL 캔버스는 살아 있는 동안 레이어 1장 +
   GPU 메모리(1600×1000×4 ≈ 6.4 MB ×DPR²). 던질 때만 만들고 끝나면 지워야 한다(지금 2D 캔버스처럼). 가능
   하지만 세 번째 렌더 경로(DOM / 2D 캔버스 / WebGL)를 유지하게 된다.
3. **얻는 것.** 주사위가 서로 부딪히고 모서리로 서는 순간 같은 "우연"이 진짜가 된다. 반대로 결과를 맞추기
   위해 눈을 바꿔 붙이는 트릭은 어차피 필요하다.

판정: 지금은 과하다. 태블릿에서 WebGL이 멀쩡히 돌아가는 것이 확인되고, B안이 모자라다고 느껴질 때
"실감 주사위(3D)" 설정으로 다시 검토.

## 3. B안(추천): 라이브러리 없는 연출 물리

지금 `tumble`을 "제자리 회전"에서 "**날아가서 벽에 튕기고 미끄러져 멈추는 궤적**"으로 바꾼다. 물리 엔진
대신 수식 몇 줄: 2D 위치/속도, 중력 대신 화면 평면 마찰, 스테이지 가장자리 네 벽에서 반사(반발 0.55),
회전 속도는 던진 속도에 비례하고 마찰로 줄며, 마지막 1/3 구간은 지금처럼 **엔진 값으로 도착하도록 회전을
계획**(`plan()`과 같은 끝맺음) + `BOUNCE`로 착지.

### 3.1 제스처 (버튼 대신)
- **차례가 오면**: 주사위 두 개가 1.2초 동안 세 번 좌우로 "꿈틀"(변환만, 페인트 0)하고 멈춘다. 5초 더
  기다리면 한 번 더 꿈틀. 상시 흔들림은 유휴 0 정책(게이트 B)과 충돌하므로 **한 번씩만**. 버튼 자리에는
  작은 안내 띠 "주사위를 꾹 누르고 밀어 던지세요"만 남긴다.
- **누르기(스테이지 가운데 넓은 투명 패드, 빨간 원 영역)**: 지금의 `shake(true)` 그대로(마구 흔들림 +
  딸깍 + 햅틱). 게이지 규칙이 켜져 있으면 게이지도 그대로 왕복.
- **밀어서 떼기**: 마지막 80 ms의 손가락 속도 벡터를 읽는다. 300 px/s 이상이면 그 방향·세기로 던진다
  (세기는 상한을 둬서 항상 2~3번 튕기고 1.2~1.6초 안에 멈춤). 그냥 떼면 지금처럼 "위로 가볍게" 던진다.
  어느 쪽이든 엔진에는 같은 `Roll`(+게이지)이 간다. **던지는 방향과 세기는 결과에 영향을 주지 않는다**
  (규칙 공정성, 결정론 유지).
- 키보드 Enter/Space: 그대로 굴림. 접근성과 e2e 유지.
- **CPU 손**: 패드를 누르고 짧게 쓸어내리는 동작으로 바꾼다(지금은 버튼을 누름). `HAND.holdRoll` 그대로.
- 설정 "굴리기 버튼 보이기"(기본 끔)로 버튼을 되살릴 수 있게 둔다. 떼기 전 손가락이 패드 밖으로 나가면
  취소가 아니라 그 방향으로 던진 것으로 본다(실수로 결과가 안 나오는 상황 방지).

### 3.2 연출
- 두 주사위는 조금 다른 속도·회전으로 출발해 벌어지며 난다. 원끼리 겹치면 밀어내는 한 줄 충돌(서로 튕김).
- 벽에 닿을 때마다 `dice-land` 변주 "딱" + 작은 먼지 퍼프 스프라이트(기존 아틀라스 파이프라인, 선택).
- 마지막 착지는 지금 `BOUNCE`(튀어 오름 → 눌림 → 복원), 더블이면 지금의 금빛.
- 총 길이 1.2~1.6초. 시간 정책은 `src/ui/fx/time.ts` 표에 한 줄 추가(동작 줄이기: 궤적 없이 제자리 굴림).

### 3.3 렌더링
- 1차: 지금의 임시 소프트웨어 캔버스에 그린다(코드 재사용, 수정 범위 `tumble` 안). 캔버스가 스테이지 전체
  크기가 되므로 그리기 비용이 커진다 → 더티 사각형(이미 반환함)만 지우고 그린다.
- 태블릿에서 굴림 캔버스가 흰 박스로 보이는 것이 확인되면(HANDOFF 열린 항목 1), 캔버스 대신 DOM 큐브
  두 개의 `pose()`를 30 Hz로 직접 갱신하는 경로로 바꾼다. 면 6장이 2D 변환이라 주사위당 레이어 1장.

### 3.4 작업량과 검증
| 단계 | 내용 | 예상 |
|---|---|---|
| 1 | 패드 + 속도 벡터 + 궤적/벽 반사 + 엔진 값 도착, 버튼 숨김·설정, CPU 손 쓸기 | 1일 |
| 2 | 두 주사위 충돌, 벽 "딱" 소리, 먼지 퍼프, 차례 시작 꿈틀, 문서·e2e | 1일 |
- e2e: `cpu-hand`, `human`, `pacing` 갱신 + 새 `dice-throw.spec`(네 방향으로 밀기 → 결과가 엔진 값과 같음,
  보드 밖으로 안 나감, 1.6초 안에 멈춤, 유휴 0 유지). 성능 게이트 `npm run perf` 재측정(굴림 중 Paint/s).

## 4. C안: 미리 구운 스프라이트
Blender/three로 오프라인에서 구른 프레임을 `scripts/fx/bake.mjs`로 아틀라스화. 런타임은 가장 싸고 음영이
가장 예쁘다. 그러나 최종 눈 6 × 회전 방향 4~8 × 24프레임이면 아틀라스가 수 MB, 손가락 방향을 연속으로
따라가지 못하고, 멈춘 뒤 선명한 DOM 주사위와 이어 붙일 때 티가 난다. B안이 모자랄 때 "회전 룩"만 보강하는
용도로 재검토.
